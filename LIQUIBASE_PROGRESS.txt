--------------------------------------------------------------------------------
1. CONTEXTE ET OBJECTIFS
--------------------------------------------------------------------------------
Initialement, la base de données PostgreSQL de VisionOps AI s'appuyait sur des
fichiers de migration Alembic (0001_initial_schema.py à 0006_model_registry.py).

Pourquoi Liquibase ?
- Découplage strict entre la couche de persistance/schéma et le code applicatif
  FastAPI (SQLAlchemy).
- Capacité d'exécuter les migrations en conteneur autonome officiel avant le
  démarrage des microservices métier.
- Auditabilité native avec traçabilité complète des exécutions (table
  DATABASECHANGELOG) et verrouillage contre les courses concurrentes
  (table DATABASECHANGELOGLOCK).
- Support robuste des retours arrière (rollbacks automatisés et manuels).

>> ÉTAPE 2 : Phase 1.2 — Rédaction du ChangeSet Initial v1.0
--------------------------------------------------------------------------------
* QUOI :
  - Création du fichier : visionops-backend/db/changelog/changelog-v1.0.xml

* COMMENT :
  Le fichier a été découpé en 7 changesets modulaires, exhaustifs et auditables :

  1. ChangeSet "v1.0-01-create-enum-types" (Auteur: visionops) :
     - Création idempotente des types énumérés PostgreSQL natifs :
       * user_role      : ('admin', 'operator')
       * alert_type     : ('roi_intrusion', 'tripwire', 'loitering', 'ppe_violation', 'custom')
       * alert_status   : ('pending', 'processing', 'ready', 'failed')
       * model_role     : ('detector', 'ppe')
       * model_format   : ('onnx', 'pytorch')
     - Bloc `<rollback>` configuré pour supprimer proprement ces types en cas d'annulation.

  2. ChangeSet "v1.0-02-create-table-users" (Auteur: visionops) :
     - Table `users` (Authentification JWT et RBAC) :
       * id (UUID, clé primaire)
       * username (VARCHAR(80), unique, non nul)
       * password_hash (VARCHAR(255), non nul)
       * full_name (VARCHAR(160))
       * role (type enum user_role, défaut 'operator')
       * is_active (BOOLEAN, défaut true)
       * created_at & updated_at (TIMESTAMPTZ, défaut NOW())
     - Index unique dédié : `ix_users_username`.

  3. ChangeSet "v1.0-03-create-table-cameras" (Auteur: visionops) :
     - Table `cameras` (Sources vidéo RTSP et caméras réseau) :
       * id (UUID, clé primaire)
       * name (VARCHAR(120), unique, non nul)
       * source_url (VARCHAR(512), non nul)
       * location (VARCHAR(255))
       * is_active (BOOLEAN, défaut true)
       * created_at (TIMESTAMPTZ, défaut NOW())

  4. ChangeSet "v1.0-04-create-table-roi-zones" (Auteur: visionops) :
     - Table `roi_zones` (Zones d'intérêt, règles de loitering et conformité EPI) :
       * id (UUID, clé primaire)
       * camera_id (UUID, clé étrangère vers cameras(id) ON DELETE CASCADE)
       * name (VARCHAR(120), non nul)
       * points (JSONB, coordonnées des polygones)
       * color (VARCHAR(32), défaut '#ef4444')
       * max_allowed_objects (INTEGER, défaut 0)
       * forbidden_classes (JSONB)
       * loitering_seconds (INTEGER, défaut 0)
       * schedule_enabled (BOOLEAN, défaut false)
       * schedule_start (VARCHAR(5), défaut '00:00')
       * schedule_end (VARCHAR(5), défaut '23:59')
       * schedule_days (JSONB, défaut '[0, 1, 2, 3, 4, 5, 6]')
       * schedule_timezone (VARCHAR(64), défaut 'UTC')
       * require_hardhat (BOOLEAN, défaut false)
       * is_active (BOOLEAN, défaut true)
       * created_at (TIMESTAMPTZ, défaut NOW())

  5. ChangeSet "v1.0-05-create-table-alerts" (Auteur: visionops) :
     - Table `alerts` (Incidents de sécurité détectés et workflow opérateur) :
       * id (UUID, clé primaire)
       * camera_id (UUID, clé étrangère vers cameras(id) ON DELETE SET NULL)
       * alert_type (type enum alert_type)
       * status (type enum alert_status, défaut 'pending')
       * incident_status (VARCHAR(32), défaut 'open')
       * zone_name, class_name, track_id, confidence, message, metadata_json
       * assigned_to, acknowledged_by, acknowledged_at, resolved_by, resolved_at, resolution_note
       * source_video_path, frame_index, snapshot_object_key, clip_object_key, error_message
       * created_at & updated_at (TIMESTAMPTZ, défaut NOW())

  6. ChangeSet "v1.0-06-create-table-alert-events" (Auteur: visionops) :
     - Table `alert_events` (Historique immuable d'audit des actions sur incidents) :
       * id (UUID, clé primaire)
       * alert_id (UUID, clé étrangère vers alerts(id) ON DELETE CASCADE)
       * event_type (VARCHAR(40), non nul)
       * actor (VARCHAR(120))
       * message (TEXT, non nul)
       * metadata_json (JSONB)
       * created_at (TIMESTAMPTZ, défaut NOW())
     - Index d'accès rapide : `ix_alert_events_alert_id`.

  7. ChangeSet "v1.0-07-create-table-model-artifacts" (Auteur: visionops) :
     - Table `model_artifacts` (Registre des modèles IA ONNX / PyTorch stockés dans MinIO) :
       * id (UUID, clé primaire)
       * name (VARCHAR(120), indexé)
       * version (VARCHAR(64), non nul)
       * role (type enum model_role, indexé)
       * format (type enum model_format)
       * filename, object_key, sha256, size_bytes
       * is_active (BOOLEAN, défaut false)
       * notes, created_by, created_at, activated_at
     - Contrainte d'unicité : `uq_model_role_name_version` sur (role, name, version).
     - Index : `ix_model_artifacts_name` et `ix_model_artifacts_role`.

* POURQUOI :
  - Transcrire rigoureusement à 100% l'intégralité du modèle de données défini
    dans app/models.py et les révisions Alembic 0001 à 0006.
  - Préserver le comportement PostgreSQL natif (types UUID, JSONB, ENUM, intégrité
    référentielle CASCADE et SET NULL, valeurs par défaut).

>> ÉTAPE 3 : Phase 1.3 — Intégration Docker Compose
--------------------------------------------------------------------------------
* QUOI :
  - Modification de : docker-compose.yml
  - Déclaration du service conteneurisé `liquibase` utilisant l'image officielle
    `liquibase/liquibase:4.29` (version stable incluant nativement le pilote JDBC PostgreSQL).
  - Mise à jour de la directive `depends_on` du service `backend` pour attendre
    `liquibase` avec `condition: service_completed_successfully`.

* COMMENT :
  - Montage de volume : `./visionops-backend/db/changelog:/liquibase/changelog`
  - Recherche du changelog : `--search-path=/liquibase/changelog`
  - Chaîne de connexion JDBC dynamique :
    `jdbc:postgresql://postgres:5432/${POSTGRES_DB:-visionops_db}`
  - Mode d'exécution one-shot : `restart: "no"`, commande `update`.
  - Condition d'orchestration :
    `postgres (healthy)` -> `liquibase (completed successfully)` -> `backend (healthy)` -> `worker`.

* POURQUOI :
  - Assurer l'automatisation complète sans intervention manuelle.
  - Empêcher l'API FastAPI et les Workers Celery de démarrer tant que le schéma
    de base de données n'est pas 100% à jour.
